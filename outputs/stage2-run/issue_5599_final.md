# Issue #5599 要約: スキャンモードがスキップ済みアイテムで終わった後の再起動で、そのアイテムが再処理される問題
## 概要
`ChunkOrientedStep` のチャンクスキャン(書き込み失敗時にアイテムを1件ずつ処理し直す動作)で、スキャン最後のアイテムが書き込み時にスキップされ、次のコミット前にステップが失敗すると、再起動時にスキップ済みアイテムが再処理される不具合です。#5558 で入ったリグレッションで、未リリースの 6.0.6 / 6.1.0-RC1 スナップショットのみが対象です。この症状については 6.0.5 は正常に動作します。ラベルは `type: bug`、`in: core`、`for: backport-to-6.0.x`、マイルストーンは 6.1.0-RC1 で、closed です。

## 問題
再現条件は次のとおりです。
- アイテム `1`〜`10`、チャンクサイズ 5、`AbstractItemCountingItemStreamItemReader` 系の再起動可能なリーダー。
- `5` の書き込みが skippable な例外、`8` の書き込みが non-skippable な例外で失敗する。

手順は次のとおりです。
1. チャンク `[1..5]` をスキャンし、`1`〜`4` は書き込まれ、`5` はスキップされる。続くチャンク `[6..10]` が `8` で失敗し、ステップが失敗する。
2. 失敗要因を取り除いて再起動する。

期待は `6` から再開し、`1, 2, 3, 4, 6〜10` が書かれることです。実際は `5` も再処理されます。原因が解消していれば書き込まれ、解消していなければ再度スキップされて `SkipListener#onSkipInWrite` に2回通知されます。リファレンスにはスキップメソッドは1アイテムにつき1回だけ呼ばれるとあり、これにも反します。

`skipLimit(1)` で `5` と `6` の書き込みが失敗し、2つ目のチャンクのスキャンでスキップ上限超過により失敗する場合も同様です。

また、スキャン対象チャンクの全アイテムがスキップされると、スキャン中にコミットが一度も行われず、再起動がそのチャンクの先頭からになります。これは 6.0.5 から存在していた問題です。

原因はコメントによると、スキップされたアイテムのトランザクションがロールバックされるため、スキップが次のコミットでしか保存されない点にあります。

## 修正内容
修正は2段階です。

**初回PR(#5600)**
- 対象は `ChunkOrientedStep` です。
- スキャンがスキップで終わった場合に、リーダーの再開位置(スキャンオフセット)をスキップ位置の先まで進めます。リーダーが状態を持つ場合のみで、この位置はメモリ上のみで保持され、次のコミットで置き換わるか、ステップ終了時に保存されます。
- この処理はスキャン最後のアイテムがスキップされたときに呼ばれるため、全アイテムがスキップされるケースも対象になります。
- テストは `ChunkOrientedStepScanModeRestartIntegrationTests` に3件追加されました。スキップで終わるスキャン後の再起動、同 concurrent モード、全アイテムスキップのケースです。

**メンテナーの追加コミット**
入力に diff はなく、以下はコメントの記述に基づきます。初回PRで未対応だった2点を扱います。
1. スキップから次のコミットの間に JVM がクラッシュするケース。初回PRは再開位置をメモリ上でしか進めないため、再起動で `5` が再処理されました。6.0.5 は正しく動くため、これもリグレッションです。
2. スキャン途中のスキップ後、次のスキャンコミット前に失敗するケース。例として `[1..5]` で `1` を書き、`2` をスキップし、`3` で non-skippable 例外が出ると、再起動で `2` が再処理されました。6.0.5 では `3`〜`5` が失われており(#5558)リグレッションではありませんが、同じ根本原因です。

修正は、ロールバックされたアイテムのトランザクションの直後に、スキップを専用のトランザクションでコミットする方式です。スキャンオフセットをスキップしたアイテムの先へ進め、最後のスキャン対象アイテムだった場合は、チャンク終端の通常のリーダーチェックポイントを取ります。テストも追加され、スキップで終わったスキャン直後のステップ停止や、再起動時に `SkipListener` へ再通知されないことも確認されています。

## 利用者への影響・対応
- 影響を受けるのは、スキップ(`SkipListener#onSkipInWrite`)を使い、再起動可能なリーダーでチャンクスキャンが動く構成です。再起動時の二重書き込みや二重通知が起こり得ます。
- 今回のリグレッション(スキャン最後のアイテムのスキップ)の影響範囲は未リリースのスナップショットに限られます。スナップショットを使っている場合は修正後のものに更新してください。修正版の具体的な番号は入力にありません。なお 6.0.5 には、全アイテムスキップ時に再起動がチャンク先頭からになる問題や、スキャン中のスキップ後に失敗するとアイテムが失われる問題(#5558)が別途存在します。
- コメントによると、`saveState(false)` のリーダーは、スキャン中のスキップごとに1回、他のコミットと同様に update されるようになります。

## 補足
- 全アイテムがスキップされるケースは 6.0.5 から存在し、初回PRのテスト(`testRestartAfterFailureInTheChunkFollowingAScanThatSkippedAllItems`)で扱われています。初回PRの実装は最後のスキップで再開位置を更新するため、このケースも対象に含まれます。
- 追加コミットの diff は入力にないため、最終的な実装の詳細は確認できていません。

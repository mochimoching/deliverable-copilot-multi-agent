# Issue #5558 要約: `ChunkOrientedStep` のチャンクスキャン中の失敗後に再起動すると、未書き込みアイテムが黙って失われる

## 概要
`ChunkOrientedStep`(6.0 で導入)で、チャンクのスキャン(書き込み失敗後にアイテムを1件ずつ再試行する処理)中にステップが失敗し、そのジョブを再起動すると、そのチャンクの未書き込みアイテムが処理されないまま `COMPLETED` になります。報告された環境は Spring Batch 6.0.5 と `main`(c15bfcea7)、Java 25 + H2 です。ラベルは `type: bug` / `in: core` / `for: backport-to-6.0.x`、マイルストーンは 6.1.0-RC1 で、Issue は closed です。本要約が参照する修正差分は commit f01627d83973 です。

## 問題
再現条件は、1チャンク5件、状態を保存する再開可能なリーダー(`FlatFileItemReader`、`JdbcCursorItemReader`、`AbstractItemCountingItemStreamItemReader` 系など)、アイテム `2` と `4` でスキップ可能な例外を投げる writer、`faultTolerant()` + `skipLimit(1)` です。

1. 初回実行: チャンク書き込みが失敗してスキャンに入り、`1` を書き込み、`2` をスキップ、`3` を書き込み、`4` でスキップ上限を超えてステップが `FAILED` になります。`1` と `3` はコミット済みで、保存されたリーダー状態(`read.count`)は `5` です。
2. データを直して再起動すると、`readCount=0` で読み込みなしのまま `COMPLETED` になり、`4` と `5` は書かれず、欠落を示す表示もありません。

原因は、スキャン中に各アイテムが個別のトランザクションで再試行され、コミットのたびにリーダーの `ItemStream#update` が呼ばれる点です。この時点でリーダーはチャンク全体を読み終えているため、コミット済みなのは失敗アイテムより前だけなのに、チャンク末尾の位置が保存されます。

Spring Batch 5 の `FaultTolerantStepBuilder` は `ChunkMonitor` でスキャン中のリーダー状態更新を抑え、代わりにオフセット(`ChunkMonitor.OFFSET`)を保存していました。`ChunkOrientedStep` には同等の仕組みがなく、移行したジョブにとっては退行です。コメントでは、v5 の実際の出力は Issue 本文の `1, 3, 4, 5` ではなく `1, 3, 3, 4, 5`(`3` が二重書き込み)と訂正されています。スキップした `2` ではオフセットが進まないためです。つまり v5 の「重複」から v6 の「黙ったデータ欠落」への退行です。メンテナのコメントで示された方針は、v5 の挙動を単純に復元するのではなく、オフセットを「コミット済みアイテム数」ではなく「読み取り位置」で数えることです。この方針が差分でどこまで実現されたかは「修正内容」に分けて記します。

## 修正内容
ここに記すのは、参照した差分(commit f01627d83973)の内容です。この差分が対象とするのは「スキャンがスキップで終わり、その後のチャンクで失敗する」ケースです。Issue 本来のシナリオ(スキャン自体が失敗で終わる場合)がこの差分で修正されるかどうかは、入力からは不明です。

差分は `spring-batch-core/src/main/java/org/springframework/batch/core/step/item/ChunkOrientedStep.java` と、テスト `ChunkOrientedStepScanModeRestartIntegrationTests.java` に及びます。

- 状態を保存する再開可能なリーダーの場合、スキャンの最後のアイテムがスキップされた時点で読み取り位置を記録します。これにより、次のコミット前に失敗して再起動しても、スキップ済みのアイテムを再処理しません。
- この位置はメモリ上のみで保持され、次のコミットで置き換わるか、なければステップ終了時に `ExecutionContext` とともに保存されます。
- テストを3件追加しました。いずれも後続チャンクで非スキップ例外により失敗させ、再起動で再処理されないことを確認します。(1) 最後のアイテムのスキップで終わるスキャン、(2) 同条件の並行モード、(3) 全アイテムがスキップされるスキャン。

## 利用者への影響・対応
`ChunkOrientedStep` + `faultTolerant()` + `skip` + 再開可能リーダーの構成で、v5 の `FaultTolerantStepBuilder` から移行したジョブが主な対象です(この範囲は Issue の記述からの整理です)。スキャン中の失敗後に再起動するジョブでは、欠落が通知されないため注意が必要です。

業務上は、該当構成のジョブの棚卸しと使用バージョンの確認、失敗後の再起動時に入出力の件数を突合する運用が考えられます(いずれも推測に基づく提案です)。修正が含まれるリリースは、マイルストーンの 6.1.0-RC1 以外は入力から確認できません。

## 補足
- Issue 本文が言及する PR #5559 の内容と、本差分(commit f01627d83973)の関係は不明です。差分は1コミット分のみで、`CHUNK_SCAN_OFFSET`、`ChunkTracker`、`isScanMode()` の既存実装を含みません。そのため Issue の元のシナリオ(スキャンが失敗で終わる場合)をこの差分単体でどう直すかは読み取れず、差分は「最後のアイテムのスキップで終わるスキャン」の追加ケースへの対応に見えます(推測)。
- 6.0.x へのバックポートの実施有無、#5493 の詳細、v5 との完全な挙動等価性は不明です。
- 影響を受けるリーダーの範囲は、Issue では「状態を保存する任意のリーダー」とされ、網羅的な一覧はありません。
- 再現が確認された環境は Java 25 + H2 のみです。

# スキップされたアイテムで終わったチャンクのスキャン後にリスタートすると、そのアイテムが再度処理される

**Issue番号**: #5599
**状態**: closed | **作成者**: beyondwin | **作成日**: 2026-10-15
**ラベル**: type: bug, in: core, for: backport-to-6.0.x
**マイルストーン**: 6.1.0-RC1
**URL**: https://github.com/spring-projects/spring-batch/issues/5599

## 内容

**バグの説明**

#5558（`0d20e2e60`、`6.0.x` へは `b527150d9` としてバックポート）によるリグレッションです。まだリリースされておらず、6.0.6 と 6.1.0-RC1 のスナップショットに影響します。

スキャンされたチャンクの最後のアイテムが write 時にスキップされ、その後、次のコミットの前にステップが失敗すると、リスタートはそのチャンクの途中から再開し、スキップされたアイテムを再度処理します。スキップの原因が解消されていればそのアイテムは書き込まれ、解消されていなければ再びスキップされ、`SkipListener#onSkipInWrite` に 2 回目の報告がされます。6.0.5 ではチャンクの後から再開します。

**環境**

Spring Batch `main` (afd4f4e66) および `6.0.x` (293410b30)、Java 25、H2。

**再現手順**

アイテム `1` から `10`、チャンクサイズ 5、リスタート可能な reader（任意の `AbstractItemCountingItemStreamItemReader`）で、`5` の write がスキップ可能な例外で失敗し、`8` の write がスキップ不可能な例外で失敗するものとします:

1. チャンク `[1..5]` がスキャンされます: `1` から `4` が書き込まれ、`5` がスキップされます。続いてチャンク `[6..10]` が `8` で失敗し、ステップが失敗します。
2. 失敗を取り除いてジョブをリスタートします。

`skipLimit(1)` でも、`5` と `6` の両方の write が失敗する場合に同じことが起こります: 2 番目のチャンクのスキャンは、スキップ上限を超えるため `6` で失敗します。

関連して、スキャンされたチャンクのすべてのアイテムがスキップされた場合、スキャン中は何もコミットされず、リスタートはそのチャンクの先頭から再び始まります。このケースは 6.0.5 にすでに存在します。

**期待される動作**

リスタートは `6` から再開し、`1, 2, 3, 4, 6, 7, 8, 9, 10` が書き込まれます。実際には `5` も書き込まれます。`5` が依然として失敗する場合は、スキップされて再度報告されますが、リファレンスドキュメントには skip メソッドはアイテムごとに 1 回だけ呼び出されると書かれています。

**Minimal Complete Reproducible example**

`testRestartAfterFailureInTheChunkFollowingACompletedScan` の隣にある `ChunkOrientedStepScanModeRestartIntegrationTests` の失敗するテストが、リンクされた pull request に含まれています。

### コメント 2 by fmbenhassine (2026-10-15)

詳細なレポートと PR をありがとうございます @beyondwin！ `main` と `6.0.x` で問題を確認し、6.0.5 とも照らし合わせました: スキャンされたチャンクのすべてのアイテムがスキップされるケース（6.0.5 にすでにあったもの）も含め、あなたが説明したすべてのケースは正しいです。

PR は 25c6141b4（`main`）と f01627d83（`6.0.x`）でマージされました。PR がまだカバーしていなかった 2 つのケースのために、フォローアップコミット 67f450d6b（`main`）と 4ea60a82e（`6.0.x`）を追加しました。どちらも根本原因は同じです: スキップされたアイテムのトランザクションはロールバックされるため、スキップは *次の* コミットによってのみ保存されます。

1. **スキップと次のコミットの間のクラッシュ。** PR はスキャンオフセットをメモリ上でのみ移動していたため、保存されるのはステップが正常に終了したとき（失敗または停止の後）だけでした。チャンク `[6..10]` の処理中に JVM が落ちた場合、リスタートは依然として `5` を再度処理していました。6.0.5 ではこのケースは正しく処理されるため、リグレッションは依然として残っていました。
2. **スキャンの途中でのスキップの後、次のスキャンコミットの前に失敗するケース。** たとえば、チャンク `[1..5]` で、スキャンが `1` を書き込み、`2` をスキップし、その後 `3` でスキップ不可能な例外により失敗する場合です。リスタートは `2` を再度処理しました（書き込まれるか、スキップされて 2 回目の報告がされる）。これはリグレッションではありません（6.0.5 ではこの場合 `3`、`4`、`5` が失われており、それが #5558 です）が、この issue と同じ問題です。

どちらも、ロールバックされたアイテムのトランザクションの直後に、スキップを独自のトランザクションでコミットすることで修正されます: スキャンオフセットはスキップされたアイテムの先へ移動されるか、それが最後にスキャンされたアイテムだった場合は、チャンクの終端に対して通常の reader チェックポイントが取られます。つまり、`saveState(false)` の reader は、他のコミットと同様に、スキャン中のスキップごとに 1 回更新されるようになります。

両方のケース、およびスキップで終わったスキャンの直後の stop のケース、さらにリスタート時にスキップが `SkipListener` に再度報告されないことの確認のためのテストが、`ChunkOrientedStepScanModeRestartIntegrationTests` に追加されています。

あらためて、コントリビューションをありがとうございます！

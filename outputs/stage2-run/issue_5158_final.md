# Issue #5158 要約: リモートパーティションのコントローラ再起動時に、完了済みワーカーステップが aggregator に渡されない問題
## 概要
リモートパーティション構成(コントローラ+ワーカー)で、コントローラの Job が停止している間にワーカー側のステップが完了し、その後コントローラを再起動すると、aggregator に空のステップ実行リストが渡される問題です。メンテナが認識している症状は、全パーティションが成功していても、再起動後のコントローラ Job が失敗扱い(FAILED)のままになり、完了しないことです。Spring Batch 6.1.0-RC1 で、コミット `57558bd35` により修正されました。報告者は Spring Boot 4.0.0 / Batch 6.0.0 を使用しており、「Batch 5 でも同じ問題がある」と述べています(5 系への修正の有無は入力からは不明です)。

## 問題
- 全パーティションが成功していても、再起動後のコントローラ Job が FAILED になります(メンテナ fmbenhassine の認識。本件の中核の症状です)。なお、空リストと FAILED の因果関係の詳細は入力に明示されておらず、未確認です。
- 報告者の説明では、`SimpleStepExecutionSplitter` が完了済みの実行を除外して返すため、再起動後の aggregator に渡されるリストが空になります。
- 当初は「再実行対象のみを返す現在の仕様どおり」という見解(banseok1216)もありましたが、メンテナは上記の失敗扱いをバグと判断し、Issue を再オープンしました。
- メンテナによる原因分析:`SimpleStepExecutionSplitter.split()` は「再実行が必要な実行のみを返す」仕様で、これ自体は正しい挙動です。本当の問題は `PartitionStep` が、`PartitionHandler` の結果を「今回実行したパーティション」と「集約すべきパーティション」の両方に使っていた点で、再起動時に後者が前者に縮退していました。
- 関連する問題として、再起動後のマネージャステップの集約メトリクスも誤っていました。例:完了1・失敗1(各3件書き込み)の場合、1回目は `writeCount=6` で正しいが、再起動後は COMPLETED でも `writeCount=3`(本来は6)になります。

## 修正内容
`SimpleStepExecutionSplitter` の仕様は変更せず、`PartitionStep` 側で集約対象を補完する方針です(`split()` が完了済みを返すと、`split()` を直接呼ぶ `PartitionHandler` が完了済み作業を再ディスパッチしかねないため、とのメンテナの説明)。

- 再起動時に、今回再実行したパーティションに加え、同一 `JobInstance` の過去の実行で完了済みのパーティションも aggregator の集約対象に含めるようになりました。
- リモート側の集約でも、現在の `JobExecution` に属さない過去の完了済み実行が落とされず、集約に反映されるようになりました。
- テスト(全完了後の再起動/一部完了後の再起動、別 `JobExecution` の実行の集約)とドキュメント(`scalability.adoc`)が追加・追記されています。

## 利用者への影響・対応
- 再起動時に aggregator が受け取る集合が「今回再実行した分のみ」から「完了済み分を含む全体」に変わります。
- 想定される確認観点(入力に根拠のない推測です):再起動時の挙動に依存した独自の `StepExecutionAggregator` や、再起動後のメトリクス(`writeCount` など)を参照する処理があれば確認が必要かもしれません。
- 修正済みバージョンは 6.1.0-RC1 のマイルストーンです。Batch 5 系への反映は入力からは分かりません。
- カスタム `PartitionHandler` を使う場合の挙動差や、過去の `JobExecution` を毎回取得することの性能影響は、入力に記載がなく不明です。

## 補足
- 差分のテストはユニットテスト中心で、リモート環境(batch-integration)での実機検証結果は入力にありません。
- 報告者の再現リポジトリは外部 URL のため未参照です。
- PR #5318(answndud 氏、splitter 側で完了分を含める案)をメンテナが採らなかったのは、splitter が完了済みを返すと再ディスパッチされるおそれがあるためです。

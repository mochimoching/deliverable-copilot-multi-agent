## 課題概要

`ChunkOrientedStep` で、チャンクの**スキャン中**にステップが失敗した後にジョブを再起動すると、そのチャンクの未処理アイテムが**エラーも出ないまま失われる**という課題です（[#5558](https://github.com/spring-projects/spring-batch/issues/5558)）。

**注意**: 今回の commit が直すのは、スキャンが「最後のアイテムのスキップ」で終わるケースだけです。下の再現条件（`4` でスキップ上限を超えて失敗するケース）が直るかどうかは、公開情報からは分かりません。バージョンアップの判断にはこの点に注意してください。

**用語補足**
- **スキャン（スキャンモード）**: フォールトトレラントなステップで、チャンクの書き込みが失敗したときに、アイテムを1件ずつ別のトランザクションで再試行し、問題のアイテムを特定する動作です。
- **`ItemStream#update`**: コミットのたびに呼ばれ、リーダーの読み込み位置（`read.count` など）を `ExecutionContext` に保存します。再起動時はこの値から再開します。
- **`ChunkMonitor`**: Spring Batch 5 の `FaultTolerantStepBuilder` が使う内部クラスです。スキャン中のオフセット（再開位置）を保存していました。

### 再現条件

- チャンク: 5アイテム（1〜5）の単一チャンク
- リーダー: 状態を保存する再起動可能なリーダー（`FlatFileItemReader`、`JdbcCursorItemReader`、`AbstractItemCountingItemStreamItemReader` 等）
- ライター: アイテム `2` と `4` でスキップ可能な例外を投げる
- 設定: `faultTolerant()` + `skip(IllegalStateException.class)` + `skipLimit(1)`

### 発生の流れ

1. チャンクの書き込みが失敗し、スキャンが始まります。
2. `1` は書き込み成功、`2` はスキップ、`3` は書き込み成功となります。
3. `4` でスキップ上限を超え、ステップが失敗します。
4. `1` と `3` は、それぞれ別のトランザクションでコミット済みです。
5. 各コミットの `ItemStream#update` 時点で、リーダーはチャンク全体を読み終えています。
6. そのため `read.count=5`（チャンク末尾）が保存されます。
7. データを修正して再起動すると、`read.count=5` から再開します。
8. `4` と `5` は読み込まれず、ステップは `readCount=0` で `COMPLETED` になります。

### 期待動作と実際の動作

issue 報告者は、`3` の後から再開して `4`、`5` を書き込み、`1, 3, 4, 5` で完了することを期待しています。実際（6.0.5 / `main` c15bfcea7）は `4`、`5` が書き込まれず、欠落を示すものも何もありません。

### Spring Batch 5 との比較

v5（`FaultTolerantStepBuilder` + `ChunkMonitor`）では `1, 3, 3, 4, 5` となり、`3` が重複します。issue 本文は `1, 3, 4, 5` としていましたが、メンテナー（fmbenhassine）が検証して訂正しました。v6（`ChunkOrientedStep`）は `1, 3` で、`4`、`5` が失われます。`FaultTolerantStepBuilder` から移行したジョブでは、重複で済んでいたものが、気づけないデータ欠落になり、v5 より悪化しています。

## 原因

- 保存される再開位置が、実際にコミットされた範囲ではなく、チャンク末尾の後になっていました（発生の流れ 5〜6 を参照）。
- Spring Batch 5 の `ChunkMonitor` のように、スキャン中の再開位置を保存する仕組みが、`ChunkOrientedStep` にはありませんでした。
- 関連する [#5493](https://github.com/spring-projects/spring-batch/issues/5493) では「スキャン中の失敗はステップを失敗させるため、ジョブは再起動可能なまま」とされていました。しかし実際には、スキャンの停止位置から再開されません。
- 添付 diff から読み取れる追加の原因があります。スキャンの**最後のアイテムがスキップ**されると、そのトランザクションはロールバックされます。このため、スキャン終了時点のチェックポイントが取られません（コメントより）。

## 対応方針

### 今回の修正の範囲

[commit f01627d](https://github.com/spring-projects/spring-batch/commit/f01627d83973bb09c3c415085e47b5e7f28d98a3) が直すのは、スキャンが「最後のスキップ」で終わるケースだけです。再現条件の `4` で失敗するケースが直るかは不明です。この commit だけで issue 全体が解決したとは言えず、補完的な修正と推測されます。

この修正で、スキャンが「最後のスキップ」で終わった場合も、再起動位置がスキップ済みアイテムの後ろへ進みます。その結果、再起動時にスキップ済みアイテムを再処理しなくなります。状態を保存しないリーダーは対象外です。

テストでは、最後のスキップ、全件スキップ、並行実行の各ケースで、再起動が次のチャンクから再開することを確認しています。

### issue 本文・コメントの方針
- メンテナーは、v5 のオフセット動作をそのまま戻さず、**オフセットの意味づけを直す**方針としています。オフセットはコミットされたアイテム数ではなく、読み込み位置を数えます。

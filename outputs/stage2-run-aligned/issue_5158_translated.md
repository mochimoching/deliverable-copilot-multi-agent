# コントローラーの再起動時に、リモートパーティションのアグリゲーターへすべてのワーカーステップが渡されない

**Issue番号**: #5158

**マイルストーン**: 6.1.0-RC1

## 内容

バグの説明
コントローラーとワーカーで構成されるリモートパーティションのジョブにおいて、コントローラージョブが停止された場合（たとえば Pod が強制終了され、ジョブが正常にシャットダウンされた場合）、リモートワーカーのステップが完了し、その後コントローラージョブが再起動されると、ジョブの進行として結果をアグリゲーターに渡す段階で、リモートステップが正常に完了しているにもかかわらず、アグリゲーターには空のステップ実行のリストが渡されます。

これは、`SimpleStepExecutionSplitter` が、完了済みであることを理由に実行をフィルタリングして除外しているためです。

環境
Spring boot 4.0.0, batch 6.0.0, batch-integration 6.0.0, JDK21
ただし、これは batch 5 でも発生する問題です

再現手順

サンプルリポジトリは https://github.com/brian-mcnamara/SpringBatch6/tree/shutdownAggregator を参照してください。

（`./gradlew run` で実行できます）特に、アグリゲーターに2つのステップ実行のリストが渡されることを期待している [235行目](https://github.com/brian-mcnamara/SpringBatch6/blob/shutdownAggregator/src/main/java/com/example/batchpartitionbug/BatchPartitionBugApplication.java#L235) に注目してください。

期待される動作

アグリゲーターが呼び出されたとき、ワーカーが完了したステップが含まれているべきです。

現在の再起動の意図に基づくと、これは意図された動作のようです。

スプリッターは「今回の試行で再実行が必要なパーティション」のみを返すため、コントローラーが停止している間にすべてのワーカーがパーティションを完了した場合、Spring Batch は再実行すべきものはもうないと判断し、結果としてハンドラー/アグリゲーターには空の実行リストが渡されます。

`JobInstance` 全体（すでに完了済みのパーティションを含む）に対する最終的な集約を行いたい場合、それは現在の動作とは異なる集約の意図になります。
考えられる選択肢は次のとおりです。
• 集約の入力を「今回の試行で再実行されたパーティションのリスト」ではなく、`JobInstance` に保存されているパーティション化された `StepExecution`（すでに COMPLETED のものを含む）にするよう、集約方法を変更する。
• パーティショニングに、オプトインの集約モード（既存の動作と、完了済みパーティションを含める動作）を追加する。

### コメント 8 by fmbenhassine (2026-09-30)

57558bd35 で修正されました。上で、これが意図された動作かどうかについて議論があったため、アプローチについて簡単に補足します。`SimpleStepExecutionSplitter` はドキュメントに記載されたとおりの動作をしている、という @banseok1216 の指摘は正しかったです。`split()` は再起動が必要な実行のみを返すと規定されており、私はそれを変更したくありませんでした。スプリッターが完了済みの実行を返すようにすると、`split()` を直接呼び出す任意の `PartitionHandler` が、完了済みの作業をワーカーに再ディスパッチしてしまうことになります。

実際のバグは1段階上の `PartitionStep` にあります。`PartitionStep` は `PartitionHandler` の結果を「今ちょうど実行したパーティション」と「集約対象のパーティション」の両方として使用しています。これらは正当に異なる2つの集合であり、再起動時には後者が暗黙のうちに前者に縮退してしまいます。そこで、この修正では、ハンドラーの結果と、同じジョブインスタンスの以前の実行ですでに完了したパーティションとの和集合に対して集約を行います。二重にカウントされないよう、パーティション名をキーにしています。`RemoteStepExecutionAggregator` にも小さな変更が必要でした。現在の `JobExecution` に属さないものをすべて除外してしまっていたためです。

調査中に、ここで報告されたケースに限らない関連する問題も見つかりました。パーティション化された再起動の後は、すべてのパーティションが完了していた場合に限らず、マネージャーステップの集約されたメトリクスが誤った値になります。1つのパーティションが完了し、1つが失敗して、それぞれが3件のアイテムを書き込んだ場合:

```
run 1: managerStep -> FAILED    writeCount=6   (correct)
run 2: managerStep -> COMPLETED writeCount=3   (should be 6)
```

再起動されたマネージャーステップは、実際には6行を書き込んだ作業に対して、書き込み件数として3を永続化していました。再実行されたパーティションだけが集約されていたためです。同じ修正で、これも解消されます。

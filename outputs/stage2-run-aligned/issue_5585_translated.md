# リスナーの例外がスキャンモードではスキップ可能だが、それ以外では致命的になる

**Issue番号**: #5585
**状態**: closed | **作成者**: fmbenhassine | **作成日**: 2026-10-12
**ラベル**: type: bug, in: core, for: backport-to-6.0.x
**マイルストーン**: 6.1.0-RC1

## 内容

この課題は https://github.com/spring-projects/spring-batch/discussions/5578 から生まれました。

リスナーは例外をスローするように設計されていません。リスナーのメソッドはいずれも例外を宣言しておらず、リファレンスドキュメントでも `ChunkListener` について「エラーは実装内で処理しなければならず、そうしないとステップは終了する」と既に述べられています。これはフォールトトレラントなチャンク指向ステップの動作でもあります。チャンクの読み取り、処理、書き込み中にリスナーがスローした例外は、ステップを失敗させます。

例外が1つあります。書き込み失敗後にチャンクをスキャンする際、書き込みリスナーがスローした例外が、スキャン対象のアイテムの書き込み失敗として扱われます。そのアイテムはスキップされ、ステップは処理を続行します。そのため、同じリスナーのバグが、スキャン中はスキップ可能なのに、チャンクの最初の書き込みでは致命的になります。

これは件数の不整合にもつながります。`afterWrite` リスナーが失敗したアイテムは、書き込み済みとしてもスキップ済みとしてもカウントされます。

**期待される動作**

スキャンではリスナーの例外をスキップしないようにし、あらゆる場面で致命的になるようにすべきです。他のリスナー失敗の場合と同様に、ステップは失敗し、再開可能な状態のままであるべきです。また、`ItemReadListener`、`ItemProcessListener`、`ItemWriteListener` の Javadoc とリファレンスドキュメントにも、リスナーは例外をスローするように設計されていないことを明記すべきです。リスナーがスローした例外はスキップやリトライの対象にはならず、ステップを終了させます。現状、これを記載しているのは `ChunkListener` だけです。

**補足**

`StepListenerFailedException` は、ステップリスナーが例外をスローするように設計されていないため、既に削除予定として非推奨になっています（6.0 以降）。リスナー内の例外は、フレームワークによって読み取り/処理/書き込みの失敗として扱われる（したがってリトライ/スキップポリシーの対象になる）べきではなく、致命的なものと見なされるべきです。v5.x ではこの点に一貫性がありませんでしたが、v6 で修正されました（スキャンだけが残っていた部分です）。

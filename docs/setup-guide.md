# セットアップ手順 — Copilot マルチエージェント環境

初めてセットアップする人向けの手順です。どの環境でも、まず第1段階（対話型）で型を作り、次に第2段階（バッチ実行）へ進みます。
根拠：『Copilot マルチエージェント環境レポート』第2版、および試行・本実行で確認した挙動。

## 0. 構成要素と必要なもの

- エージェント定義4ファイル（`.github/agents/` の planner／writer／reviewer／fixer）
- 第2段階ハーネス一式（`harness.py`／`copilot_runner.py`／`validate.py`／`config.json`）
- 必要なもの：Copilot のシートが割り当てられた GitHub アカウント、VS Code（第1段階）、Copilot CLI（第2段階）、Python 3（第2段階）

## 1. 事前確認

1. 対象アカウントで GitHub にログインでき、対象リポジトリにアクセスできること。
2. Copilot のシートが割り当てられていること（VS Code で Copilot が応答すればよい）。
3. CLI を使う場合、所属プラン／組織で CLI が有効になっていること（組織管理下のアカウントではポリシーで制御される）。
4. AI Credits の上限と課金方針を確認しておくこと。プランによっては月枠を使い切っても追加利用が自動で止まらない場合があるため、実行中は消費を記録し、想定外に減りが速ければ上限を待たずに管理者・組織へ相談する。
5. `.agent.md` の frontmatter（`tools`／`handoffs`／`model` 等）の現行仕様を公式ドキュメントで確認すること。項目の効き方は実行面（VS Code／CLI／cloud）とバージョンで差がある。たとえば CLI では `handoffs` が無視される版がある（役割遷移は人が送るか、第2段階ハーネスが実行する前提で設計する）。

## 2. 手順A：エージェント定義の配置（第1段階）

1. 対象リポジトリに `.github/agents/` フォルダを作り、定義4ファイルをコピーする。
   - `planner.agent.md`（計画のみ。読み取り・検索だけ）
   - `writer.agent.md`（計画に沿った実装・執筆）
   - `reviewer.agent.md`（JSON の修正指示だけを返す。読み取り・検索だけ）
   - `fixer.agent.md`（レビューJSONの範囲だけ修正）
2. CLI でも同じ定義を使う場合は `~/.copilot/agents/` にも置けるが、**定義を二重管理しない**。正本はリポジトリ側に置く。
3. 配置後、VS Code のチャットで各エージェントが選択肢に出ることを確認する。CLI では `copilot --agent <名前>` で呼べることを最小プロンプトで確認する。

## 3. 手順B：第1段階の試行（VS Code、対話型）

1. 実作業から小さい案件を1件選ぶ（目安：半日以内に人の目で正否を判断できるもの）。
2. 流れは planner →（人が承認）→ writer →（人が承認）→ reviewer →（revise なら）fixer。各遷移は人が送る。自動マージはしない。
3. VS Code では `handoffs` が効くため、定義に沿った遷移が出るかを確認する。
4. `TRIAL.md` に記録する：面（VS Code／CLI／cloud）、消費 credits、reviewer の verdict と指摘件数、fixer が範囲外を触らなかったか、人の手戻し回数。
5. 成功基準：全遷移が定義どおりに動く／reviewer が JSON のみ返す／fixer が指摘範囲外を変更しない／消費が記録できる。2〜3件で型が固まれば第1段階は完了。

## 4. 手順C：Copilot CLI の導入（第2段階の下準備）

1. 導入方法は公式の現行手順に従う（npm `@github/copilot`、winget、Homebrew 等。導入時に公式リファレンスで確認）。
2. `copilot login` で、作業に使うアカウントでログインする。複数のアカウントを使い分ける環境では、ログイン中のアカウントを取り違えないこと。
3. 疎通確認は表示上の状態ではなく、最小の実呼び出し（短い応答を求めるプロンプト）で行い、消費 credits が表示されることを確認する。
4. 利用できるモデルはプランと組織設定で変わる。**ハーネスの config のモデル名は、実際に呼べることを確認してから固定する**（例：呼べたモデルが `claude-sonnet-5.5` なら、その名前を設定する）。

## 5. 手順D：第2段階ハーネスの配置（バッチ実行）

1. 前提：Python 3 が使えること。ハーネス一式を作業フォルダにコピーする。
2. `config.json` の見直しポイント（項目名は実装どおり）：
   - `model`：手順Cで確認した、実際に呼べるモデル名に合わせる。
   - `copilot_bin`：Copilot CLI の実行ファイルのパス。自分の環境の導入先に書き換える。
   - `input_base`：入力ファイル（原文と差分）の置き場所。自分の題材の置き場所に書き換える。
   - `budget_warn_credits`／`budget_stop_credits`：予算ガード。自分のプランの月枠に合わせて決める。目安は「月枠の2割で警告、4割で停止」程度から始め、消費ペースを見て調整する（月枠1,500 の例：warn 300／stop 600）。
   - `diff_max_chars`（入力の切り捨て上限）／`input_warn_chars`（入力サイズ警告の閾値）：題材の平均的な入力サイズに合わせて調整する。
   - `required_sections`／`summary_template_sections`：成果物の必須セクションとテンプレート。現行値はガイドラインの構成（課題概要／原因／対応方針）にそろえてある。題材が変われば差し替える。
   - `guidelines_dir`／`guideline_files`：役割の基準になるガイドラインの置き場所。ガイドライン3本（TRANSLATION／SUMMARY／REVIEW）はハーネスの `guidelines/` に同梱され、既定は相対指定の `guidelines`（ハーネスの置き場所を基準に解決）。ハーネスが実行時に読み込んでプロンプトに全文を渡す。別の場所に置く場合はここを書き換える（絶対パスも可）。
   - `exclude_issues`：実行対象から外す件の指定。対象リストの作り方に合わせて見直す。
   - `call_timeout_sec`（呼び出しの上限時間）／`format_retries`（形式不適合時の再実行回数）／`diff_change_warn_ratio`（fixer の変更量の警告比率）：通常は既定のままでよい。
3. 題材アダプタ：入力は「原文＋差分」の組み立て前提になっている。別の定型作業に使う場合は、入力ファイルの組み立て部分だけを題材に合わせて差し替える（進行・検証・予算ガードはそのまま使える）。
4. 実行は必ず小規模（`--limit 2`）から。検証8項目と再開（done スキップ）が働くことを確認してから件数を広げる。
5. 成果物と状態は `runs/` に残る。バッチごとに消費合計を記録する。
6. 取得と翻訳の設定（題材が GitHub issue の場合）：入力はハーネス自身が GitHub から取得できます（取得用のクライアントも同梱で、外部プロジェクトには依存しません）。認証は環境変数 `GITHUB_TOKEN` に Personal Access Token を設定するのが本線です（一部の Muse 環境では、未設定時にコネクタ経由のフォールバックも働きますが、他の環境では使えません）。`config.json` の `fetch` 節に `owner` / `repo` / `milestone` / `state` / `order` を設定し、`input_base` を null にすると、取得結果が `inputs/` に保存されてそのまま入力になります（`input_base` にパスを指定した場合は従来どおり外部フォルダから読みます）。また、流れには planner の前段に translator（全文翻訳）工程があり、翻訳はコードブロックが原文と完全一致することや見出し構造が保たれていることを機械検証します。役割の基準はガイドライン正本（`guidelines_dir`）をプロンプトに全文埋め込んで渡す方式で、AI明示と #参照のリンク化はモデルに任せずハーネスの後処理で決定的に適用します（要約の構成はガイドラインどおり課題概要／原因／対応方針、バグ issue のみ「バグの発生タイミング」が条件付きで加わります）。翻訳が不要な題材では translator 工程を飛ばせるよう、検証の下限（`translation_min_ratio`）とあわせて config で調整してください。既に要約まで終わっている件に翻訳だけを後から足す場合は、補完モード（`--backfill-translate`）を使います。

## 6. 運用ルール

- planner／reviewer に編集ツールを与えない。「書く側と見る側」の分離をツール権限で担保する。
- reviewer の出力は JSON 固定。fixer はその範囲だけ直す。範囲外の変更が要る場合は、人が判断する。
- 自動マージ・自動コミットはしない。成果物は人が確認してから取り込む。
- 消費 credits はバッチごとに記録する。
- reviewer が「pass なのに指摘を残す」ことがある。ハーネス側で「指摘があれば実効 revise」に正規化してあるので、そのまま使えば指摘が捨てられることはない。

## 7. 詰まったときの切り分け

| 症状 | 確認先 |
|---|---|
| CLI が起動しない／エージェントが選べない | CLI の有効化（プラン／組織ポリシー）、シート割り当て、ログイン中のアカウント |
| モデル名でエラーになる | そのプラン・組織で利用可能なモデル一覧（公式ドキュメント）。config のモデル名を実際に呼べるものに直す |
| `handoffs` で遷移しない | 実行面・バージョンによっては無視される仕様。遷移は人が送るか、ハーネス（第2段階）で実行する |
| 消費が想定より速い | 入力サイズが主因になりやすい（入力が大きい件では単価が2倍近くになることがある）。入力を小さく分ける、予算ガードの stop を下げる |
| ログインが外れている | 表示上の有効期限ではなく実呼び出しで確認し、再ログインする |

## 1. 目的と範囲

- 目的：決まった手順（役割分離フロー）を**大量件数に回し、機械検証まで行い、途中で止まっても再開できる**バッチ実行基盤を、Copilot CLI の上に薄く自作する。
- 対象フロー（初期）：planner → writer → reviewer → fixer の4役割。第1段階の `.agent.md` 定義をそのまま使う（VS Code／CLIで二重管理しない、という第1段階の方針を継続）。
- 非対象：対話型の支援（第1段階の範囲）、Copilot SDK への組み込み（第3段階）、Agent HQ。
- 設計原則（レポートより）：最も単純な解法を選ぶ。モデルに任せる部分と、決定的なコードで担保する部分を分ける。精度の保証はハーネス側の機械検証で持つ。

## 3. 全体構成

```
harness.py（進行役）
  ├─ 対象リスト読み込み／状態の復元（state.json）
  ├─ 件ごとに作業フォルダを用意し、役割を順に呼ぶ（直列が既定）
  ├─ copilot_runner.py … copilot -p --agent <役割> --model <固定モデル> --output-format json を新規プロセスで実行
  │     返り値：最終応答テキスト、usage（credits／tokens）、所要時間、成否
  ├─ validate.py … 決定的検証（第6章）。不合格は理由つきで記録
  └─ 予算ガード … 累積クレジットを監視し、warn／stop で制御（第7章）
```

- ファイルは4つだけに絞る：`harness.py`、`copilot_runner.py`、`validate.py`、設定 `config.yaml`（または .json）。状態は `state.json` と追記型 `run-log.jsonl`。
- 既存の `summarize.py`／`claude_runner.py`（github_issue_translate）の構造を下敷きにし、呼び出し先を `claude -p` から `copilot -p --agent` に差し替える。検証項目と「見出しより前を切り捨てるガード」等の知見は移植する。

## 4. 処理フローと状態遷移

1件のライフサイクル（状態は state.json に保持）：

`pending → planned → drafted → reviewed → (pass → verified) / (revise → fixed → verified) → done`
異常時は `failed`（理由を記録。再開時は failed から手動で戻す）。

- planner：入力（issue原文＋diff）から作業計画を作る。本文は書かない。出力は出力契約テンプレートに従う。
- writer：計画に沿って成果物（初期題材では日本語要約）を作る。
- reviewer：成果物を見て JSON のみ返す（`{"verdict": "pass"|"revise", "issues": [...]}`）。書き直しはしない。
- fixer：verdict が revise のときだけ、issues の範囲だけ直す。pass のときは呼ばない。
- verified：validate.py の決定的検証を通過した状態。done は verified ＋成果物の保存完了。

## 5. 状態管理と再開

- `state.json`：件ごとの状態、役割ごとの成否・usage・所要時間、成果物パス、検証結果、失敗理由。更新は「一時ファイルに書いてから置き換える」原子的更新にする（再起動で壊れないため）。
- `run-log.jsonl`：呼び出し単位の追記型ログ（時刻、件、役割、モデル、credits、tokens、成否）。クレジット集計と事後分析の元データ。
- 再開：起動時に state.json を読み、`done` の件はスキップし、途中状態の件は最後に成功した役割の次から再開する。二重実行・二重消費を避けるため、再開時に対象と残件数を表示する。

## 6. 決定的検証（validate.py）

モデルに任せない、コードで担保する検査：

1. review.json が JSON としてパースでき、スキーマ（verdict と issues 配列、severity の値域）に合うこと。
2. 成果物が空でないこと、必須セクション（出力契約で定めた見出し）がそろっていること。
3. 成果物の最初の見出しより前に、作業メモ等の混入がないこと（混入時は切り捨てガードを適用し、適用した事実を記録する。過去のパイプラインで実際に起きた事故への対策）。
4. fixer の変更が review の issues の範囲に収まっていることの目安として、draft と final の差分量と変更箇所を記録する（範囲外の大幅な書き換えは警告）。
5. 入力に含まれるコードブロック・識別子が成果物で欠落していないことの簡易チェック（題材ごとに項目を設定で差し替え可能にする）。
6. クレジット集計が run-log と一致すること。
7. planner 出力が出力契約のテンプレートに合っていること（第2章の要件3）。
8. 役割の権限逸脱がないこと（planner／reviewer の成果物に、対象ファイルへの書き込み形跡がないこと）。

検証に落ちた件は done にせず、理由とともに failed として残す。「検証を通ったものだけが成果物」という線引きを守る。

## 7. 予算ガード

- 設定：`budget_warn_credits`（初期値 300）、`budget_stop_credits`（初期値 600）。本人の前提（個人Proの月枠1,500、上限まで回してよい・達したら組織と相談）に対応する。
- warn 到達時：ログと進捗表示で警告し、続行する。
- stop 到達時：実行中の件を終えてから新規の件に入らず、状態を保存して停止する。再開は上限の見直し後に手動で行う。
- 集計は run-log.jsonl の実測値で行い、推定では止めない。

## 8. 権限と安全

- 役割ごとの最小権限を、エージェント定義の tools と、呼び出し側の `--allow-tool`／`--deny-tool` の両方で担保する。planner／reviewer は読み取り・検索系のみ。writer／fixer は作業フォルダ内への書き込みのみ。
- 件ごとに作業フォルダを分ける。同一ファイルへの並行書き込みは起きない構造にする（v1 は直列実行。並列化する場合も件単位で、同時実行数の上限を設定で持つ）。
- 対象は当面、私的環境のデータ（公開リポジトリ等）に限る。会社のコード・情報をこの基盤に入力しない（個人プランのデータ条項のため。第1段階で確認済みの注意を継続）。

## 9. 実行基盤と移植対応

- 実行基盤は当面ローカル（この私的環境）。GitHub Actions 変種は、実行環境に Copilot CLI と認証を用意できることが前提で、差分は「認証の渡し方」と「成果物の保存先」のみとする（将来の拡張点として分離しておく）。

| 既存（summarize.py 系） | 第2段階での扱い |
|---|---|
| claude_runner.py（`claude -p` 呼び出し） | copilot_runner.py に置き換え（`copilot -p --agent`、JSONL解析、モデル固定） |
| 執筆／レビューを別セッションにする分離 | そのまま採用（役割ごとに新規プロセス） |
| レビューの JSON 指示のみ・書き直し禁止 | そのまま採用（reviewer 定義と検証1で担保） |
| 見出しより前の混入を切り捨てるガード | 検証3として移植 |
| 全件検証（件数・空欄・コードブロック保持） | 検証2・5として移植 |
| 状態管理（バックアップと再開） | state.json＋run-log.jsonl で再設計（要件4） |

## 10. エラー処理と運用

- 実行前の事前確認：ログイン状態の表示だけで判断せず、最小の実呼び出しで疎通を確認してから本実行に入る（過去にログイン喪失を経験済みのため）。
- レート制限・認証エラーが出たら、リトライで粘らず停止して状態を保存する。
- 形式不適合のリトライは役割ごとに1回まで。それ以外は自動リトライしない（消費の暴走を防ぐ）。
- 進捗は件単位で表示し、Ctrl+C 等の中断でも state.json が壊れないこと（原子的更新）。

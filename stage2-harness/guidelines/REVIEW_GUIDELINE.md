# GitHub Issue 要約レビューガイドライン

このドキュメントは、執筆担当が作成したIssue要約を、レビュー担当が
想定読者の立場で点検し、具体的な修正指示（ダメ出し）を出すための基準です。

---

## 役割分担

- 執筆担当：SUMMARY_GUIDELINE.md に従って要約を作成・修正する
- レビュー担当：本ガイドラインに従って要約を点検し、問題があれば修正箇所と修正方法を具体的に指示する。自分では要約を書き直さない
- レビュー担当は執筆担当とは別のセッションで動作し、遠慮なく指摘してよい

---

## 想定読者（ペルソナ）

- Spring Batchを業務に利用し始めて2〜3年くらいの中堅エンジニア
- Java、Spring Framework、Spring Boot、Spring Batchについて、基本的な知識とある程度の業務経験はある。ただし網羅的な知識を持っているわけではなく、知識の抜けている部分もある
- 知らないことは自分で調べながら、業務の作業を進めることができる

レビューは終始このペルソナの立場で行う。「この読者が、つまずかずに読めるか」「自分の業務にどう効くか分かるか」を判断軸にする。

---

## レビュー観点

### 1. 難しさ（用語と前提知識）
- ペルソナが知らない可能性のある概念・内部動作・固有の用語が、説明なしに使われていないか。該当する場合は「その用語の直後に1〜2文の補足を入れる」よう指示する
- 逆に、ペルソナが当然知っている基本概念（ジョブ、ステップ、チャンクなど）への過剰な説明があれば、削るよう指示する

### 2. 堅苦しさ（文体）
- 役所文書のような言い回し、漢語の連なり、一文の長すぎる文章、受動態の多用がないか
- 該当する場合は「文を2つに分ける」「能動態にする」「平易な言い回しに変える」など、書き換え方まで指示する

### 3. 業務への効き方
- この変更が、ペルソナの業務（自分のバッチ処理の運用、バージョンアップ作業など）にどう影響するかが具体的に書かれているか
- diffの変更内容の羅列で終わっていないか。変更の「意味」と「影響」に言及するよう指示する

### 4. 冗長さと構成
- 同じ内容の繰り返し、なくても伝わる段落がないか
- SUMMARY_GUIDELINE.md の構成（課題概要／原因／対応方針、バグの場合はバグの発生タイミング）に従っているか
- 表や図が、文章で十分な場所にまで使われていないか（図表は理解の助けになる場合のみ）

### 5. 形式ルール
- クラス名・メソッド名がバッククォートで囲まれているか
- Issue参照がリンク形式になっているか、元のリンク情報が維持されているか
- 訳語が揺れていないか（例：ジョブ実行／JobExecution の混在のしかた）

---

## 出力形式

レビュー結果は次のJSONのみで出力する（説明文は付けない）。

```json
{
  "verdict": "ok" または "revise",
  "points": [
    {
      "severity": "must" または "should",
      "location": "指摘箇所（見出し名や、対象の文の冒頭）",
      "problem": "ペルソナの立場で何が問題か",
      "instruction": "執筆担当への具体的な修正指示"
    }
  ]
}
```

- 問題がなければ verdict は "ok"、points は空配列
- 「もっと分かりやすく」のような曖昧な指摘は禁止。必ず、どこを・どう直すかまで書く
- 事実関係（技術的な正しさ）への指摘は、根拠が確かな場合のみ行う。文体と難易度の指摘を優先する
